# 模型不可用与追问契约 · 需求文档

- 日期：2026-08-12
- 状态：待评审
- 关联技术方案：`docs/模型不可用与追问契约-技术方案-2026-08.md`

## 1. 背景

2026-08-12 对线上环境（https://chisha.leftzzzz.top）做了完整流程回归，发现模型供应商
额度耗尽后，产品进入不可用且用户无法自救的状态。

线上 trace 原文（`/api/agent/session/{id}?include=trace`）：

```
SUPERVISOR_UNAVAILABLE: SupervisorPlannerAgent API failed: 403 -
Free quota exhausted. To continue accessing the model on a paid basis,
please add funds or disable the "use free tier only" mode ...
model=qwen3.6-flash-2026-04-16
```

四个 Agent（Supervisor / Evaluation / KeywordExpansion / Replan）共用同一组
key 与 endpoint，因此一次配额耗尽等于全部模型能力同时失效。

### 1.1 实测行为

| 输入 | 线上表现 |
|---|---|
| 「附近有什么好吃的」 | 3 秒后进入「补充需求：想吃点什么？可以直接说菜品或菜系」 |
| 在追问处点「你推荐」 | 回到同一个问题，状态无任何变化，可无限重复 |
| 「想吃火锅」 | 高德返回 40 家真实火锅店，`accepted: 0`；连搜 4 次（火锅／涮锅／中餐／牛肉火锅）耗时 42 秒，最终追问「验证服务暂时不可用，要重试一次吗？」 |
| 在上述追问处回答「重试」 | 回到「想吃点什么？」，且会话被清空：`goal.rawQuery` 由「想吃火锅」变成「重试」，`actionCount` 5→1，`observationCount` 4→0 |

三次搜索返回的 POI id 完全重合，属于无效重复调用。

## 2. 问题定义（用户视角）

- **P1 无法自救的死循环**：追问处的所有可点选项（「你推荐」「重试」）都不会推进状态，
  用户除了刷新页面没有出路。前端在追问超过 3 轮后反而收窄为只剩「你推荐」一个按钮
  并禁用自由输入，把唯一的自救通道（打字说出菜名）关闭。
- **P2 故障被伪装成正常追问**：模型 403 时用户看到的是「想吃点什么？」，而不是
  「AI 服务不可用」。用户以为是自己没说清楚，反复尝试，实际每次都注定失败。
- **P3 会话被静默清空**：回答「重试」后，此前搜到的上百家餐厅与已理解的目标全部丢失。
- **P4 无效重试引导**：文案「服务暂时不可用，要重试一次吗？」对配额耗尽这种不可恢复
  错误是错误引导，重试 100% 失败。
- **P5 资源浪费**：模型已确定不可用的情况下，单轮仍发起 6 次注定失败的模型调用与
  3 次重复的高德搜索，单轮耗时 42 秒。

## 3. 产品原则

本次改造确立三条原则，后续所有相关改动都必须遵守：

**原则一：模型不可用时明确报错，绝不用硬编码语义顶替。**
不做"评估降级"，也不做"按词表从原话里抽菜名继续搜"。任何以关键词表冒充模型判断的
兜底逻辑一律移除。宁可告诉用户"AI 服务当前不可用"，也不给一个来路不明的推荐。

**原则二：用户意图的理解只有一个归属——Supervisor（模型）。**
「你推荐」「随便吧」「你决定」「太远了」这类自由文本，一个字都不应出现在代码常量或
关键词表里。代码只负责把上下文（previousGoal、pendingQuestion、messages）完整交给
模型，不负责猜语义。

**原则三：追问选项是协议，不是文案。**
用户点击的每一个按钮，都必须对应一个后端定义的、可确定性执行的状态转移，通过稳定的
选项 id 传递。UI 文案的任何改动都不得影响语义。

## 4. 需求条目

### R1 模型不可用一律报错（对应 P2）

- R1.1 Supervisor 调用失败时，本轮以结构化错误结束，向用户展示「AI 服务当前不可用」
  类文案，不再生成任何追问、不再发起任何搜索。
- R1.2 删除"按原文关键词搜索"的降级目标构造能力。
- R1.3 候选验证（Evaluation）调用失败时不产生任何未经验证的候选，失败的候选不进入
  主推荐，也不进入候补。
- R1.4 当本轮存在验证失败、但已有通过验证的主推荐时：正常返回结果，并在结果中附带
  一条警告说明"部分候选未能完成验证"。
- R1.5 当本轮存在验证失败、且没有任何通过验证的主推荐时：以结构化错误结束本轮。

**验收标准**
- [ ] 模型全不可用时，「附近有什么好吃的」与「想吃火锅」都以 error 事件结束，
      页面展示服务不可用提示，且不出现「补充需求」。
- [ ] 上述过程中不产生任何高德搜索调用。
- [ ] 代码中不存在从用户原话抽取菜品词用于搜索的路径。

### R2 错误分级与可恢复性（对应 P4）

- R2.1 区分错误性质并使用独立错误码：配额耗尽 / 鉴权失败（不可恢复）、限流、
  服务暂时不可用（可恢复）。
- R2.2 前端是否展示"重试"入口，完全由错误的可恢复标记决定；不可恢复错误不得出现
  重试按钮，应引导"稍后再试"或"更换需求"。
- R2.3 错误文案不得把配置/配额问题描述为"暂时"。

**验收标准**
- [ ] 配额耗尽场景下，页面不出现任何重试按钮。
- [ ] 限流（429）与网络超时场景下，重试入口正常出现。

### R3 会话在失败时保持完整（对应 P3）

- R3.1 本轮失败（任何原因）不得清空会话中已有的 goal、attempts、candidates、
  observations。
- R3.2 本轮失败不得覆盖 `goal.rawQuery`；用户上一次成功表达的需求必须保留。
- R3.3 失败后用户重新发起请求（原需求或新需求）时，能在原会话上继续。

**验收标准**
- [ ] 「想吃火锅」搜到结果后触发一次失败，会话内 `goal.rawQuery` 仍为「想吃火锅」，
      已有 observations 数量不变。

### R4 追问选项走结构化 id（对应 P1）

- R4.1 追问选项以 `{id, label}` 形式下发；客户端回传 id，不回传文案。
- R4.2 后端按 id 查找并执行对应的确定性状态转移，全程不调用模型。
- R4.3 客户端不得自行构造任何选项；页面上出现的每个选项都必须来自后端。
- R4.4 「重试」作为一个结构化动作：以当前 goal 原样重跑本轮，不修改 goal，
  不改变会话模式。
- R4.5 自由文本输入一律提交给 Supervisor 做意图理解；后端不得对自由文本做
  关键词匹配来推断"开放推荐""重试"等意图。

**验收标准**
- [ ] 点击「随便推荐」类选项时，服务端日志显示本次未发生 Supervisor 模型调用。
- [ ] 修改选项 UI 文案后，功能不受影响（存在对应测试）。
- [ ] 模型可用时，在追问处**手动输入**「你推荐」能正常进入开放推荐搜索。

### R5 追问不得原地打转（对应 P1）

- R5.1 服务端保证：同一个问题不会连续两轮抛给用户。若本轮结论与上一轮追问等价，
  必须改变策略或结束会话。
- R5.2 连续追问达到上限（3 轮）时收敛：有候选则给出结果，无候选则以明确说明结束
  并清除待答问题，允许用户重新开始。
- R5.3 客户端不得因追问轮次而禁用自由文本输入。
- R5.4 模型在追问上下文中返回一个**新的**追问属于合法行为，不得当作服务故障。

**验收标准**
- [ ] 构造模型持续返回同一问题的场景，会话在第二轮收敛，不再出现第三次相同追问。
- [ ] 任意追问轮次下，自由输入框始终可用。

### R6 失败快速终止（对应 P5）

- R6.1 一旦本轮发生候选验证失败，不再继续扩大搜索。
- R6.2 同一轮内模型连续失败达到阈值时，跳过该轮剩余的模型调用。

**验收标准**
- [ ] 模型全不可用时，单轮模型调用次数 ≤ 2，高德搜索次数为 0。
- [ ] 单轮耗时从 42 秒降至 5 秒以内。

### R7 模型配置更新

- R7.1 默认模型统一为 `deepseek-v4-flash-0731`，覆盖 `.env.example`、代码内默认值
  与全部文档。
- R7.2 保留分级模型变量（Supervisor / Planner / Evaluation / Keyword）的覆盖能力。

**验收标准**
- [ ] 仓库内不再出现 `gpt-4o` 作为默认值。
- [ ] README、CLAUDE.md、AGENTS.md 与 `.env.example` 描述一致。

## 5. 非目标

- 不引入多供应商自动切换 / 模型故障转移（后续独立议题）。
- 不改动转盘、历史记录、地图等与本次故障无关的功能。
- 不改动候选评分与排序算法。
- 不为模型输出增加缓存层。

## 7. 风险

- **会话结构变更**：`PendingQuestion` 由 `options: string[]` 变为对象数组，需对旧
  会话做一版兼容（详见技术方案第 6 节）。
- **用户可见行为变化**：模型不可用时用户不再得到任何推荐结果。这是本次的明确取舍——
  错误的推荐比没有推荐更糟。需保证错误文案清晰。
- **eval 基线变化**：追问率、主推荐数、搜索步数均会变动，需在 PR 中附基线 diff。
