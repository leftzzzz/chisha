## 1. 根因定位

线上死循环由三个独立缺陷叠加而成，缺一不可：

**缺陷 A：降级路径用词表冒充语义理解。**
`lib/agent/runtimeV3.ts:537-567` 的 `resolveTurnGoal` 捕获所有 Supervisor 异常后转入
降级，`lib/agent/degraded.ts:95-104` 的 `extractDegradedKeywords()` 用 `POI_TAXONOMY`
在用户原话里做子串匹配抽菜名，抽不到就发出固定追问
`DEGRADED_CLARIFYING_QUESTION`（`degraded.ts:83-87`）。该追问没有 options、没有
optionEffects，任何不含菜名的回答都会再次落入同一分支，原样重发同一个问题。

**缺陷 B：选项语义绑定在 UI 文案上。**
`supervisor.ts:245` 的 `deterministicClarificationAnswer` 以
`pendingQuestion.optionEffects[用户输入原文]` 精确匹配来决定确定性转移。而前端
`components/LoadingSteps.tsx:249` 硬编码了「你推荐」按钮、
`hooks/useRestaurantSearch.ts:189` 在追问超限时硬编码 `options: ['你推荐']`，
后端 `policy.ts:689` 的授权选项却叫「随便推荐」。字符串对不上 ⇒ 确定性通道恒 miss
⇒ 全部回落模型 ⇒ 模型 403 ⇒ 回到缺陷 A。

**缺陷 C：没有任何循环终止不变量。**
服务端不记录上一轮问了什么，`runtimeV3` 可以无限次抛出同一个 `ask_user`。前端的
`MAX_QUESTION_COUNT`（`useRestaurantSearch.ts:167-195`）在超限后把 UI 收窄为只剩
「你推荐」并置 `allowFreeText: false`，恰好关闭了唯一能打破循环的输入方式。

**放大器：**
- `supervisor.ts:171-174`：模型在有 pendingQuestion 时返回新问题（既无 goal 也无
  patch）被当成 `SUPERVISOR_UNAVAILABLE` 抛出，把模型的合法判断污名成服务故障，
  再次落入缺陷 A。
- `runtimeV3.ts:554,563`：降级结果写死 `conversationMode: 'start_new_goal'`，经
  `deriveSearchStateResetPlan` 清空 attempts/candidates/actions/observations。
- `runtimeV3.ts:1063-1067`：评估失败时用 `buildUnverifiedEvaluationFallback` 产出
  `status: 'unverified'` 候选，被 `finalGuard.ts:58` 挡在主推荐外，`policy.ts` 因此
  认为"一个结果都没有"，继续按 `policy.ts:204` 换镜头扩搜，产生重复的高德调用。
- `modelClient.ts:414-417`：仅 429/5xx 判为可重试，403 落到 `UNKNOWN`；而
  `runtimeV3.ts:547` 又把降级信息硬编码为 `retryable: true`。

## 2. 设计决策

### D1 移除全部模型降级路径，失败即错误

- 删除 `lib/agent/degraded.ts` 及其全部引用（`runtimeV3.ts:17-19,544-566`）与测试
  `__tests__/lib/agent/degraded.test.ts`。
- `resolveTurnGoal` 不再捕获异常：Supervisor 抛出的 `AgentError` 直接向上传播，由
  `runSearchAgentV3` 顶层包成 `AgentRunError` 交给 route 发 SSE `error`。
- 关键点：**目标解析发生在 `createInitialContext` 之前**，此时 `contextRef.current`
  为空，`route.ts:316-325` 不会调用 `applyRuntimeStateToSessionAsync`，会话状态天然
  保持不变（满足 R3）。需补测试锁死这一行为。
- 删除 `buildUnverifiedEvaluationFallback`；`evaluatePlanCandidates`
  （`runtimeV3.ts:1002-1092`）捕获评估异常后只记录失败，不再合成候选。

### D2 评估失败的两种收敛

`AgentV3Context` 的 `evaluationDegraded: boolean` 更名为 `evaluationFailed`，并新增
`evaluationError?: AgentError`，语义由"降级"改为"发生过失败"。

策略层（`policy.ts` `decideNextAction`）新增最高优先级分支：

```ts
if (ctx.evaluationFailed) {
  return hasPrimaryCandidates(ctx)
    ? finishDecision(ctx, 'PARTIAL_EVALUATION_FAILURE', 0.6)   // R1.4
    : { kind: 'abort', reason: 'EVALUATION_FAILED' };          // R1.5
}
```

- 新增 `PolicyDecision` 分支 `{ kind: 'abort'; reason }`，Runtime 见到即抛出
  `context.evaluationError ?? new AgentError(..., 'EVALUATION_FAILED', ...)`。
  策略层保持纯函数，不负责抛错。
- `FinishReason` 新增 `PARTIAL_EVALUATION_FAILURE`，`finishReason.ts` 增加对应用户
  文案：「部分餐厅没能完成验证，以下是已确认符合的结果」。
- `AgentFinalResult` 与 SSE `final` 事件新增 `warnings?: string[]`，承载 R1.4 的提示；
  不复用 `unmetConstraints`（语义不同）。
- 删除 `policy.ts:604-611` 中基于 `evaluationDegraded` 生成的「要重试一次吗？」追问——
  该场景现在走 error 或 finish，不再追问。

这条同时满足 R6.1：一旦评估失败立即停止扩搜，不会再出现「火锅／涮锅／中餐」重复搜索。

### D3 错误码分级

`AgentErrorCode` 扩展为：

```ts
export type AgentErrorCode =
  | 'SESSION_EXPIRED'
  | 'CONFIG_MISSING'          // 401 / 缺少 key，不可恢复
  | 'MODEL_QUOTA_EXHAUSTED'   // 402 / 403 配额，不可恢复      【新增】
  | 'MODEL_UNAVAILABLE'       // 5xx / 超时 / 网络，可恢复      【新增】
  | 'RATE_LIMITED'            // 429，可恢复
  | 'SUPERVISOR_UNAVAILABLE'  // 保留：模型返回结构不合法
  | 'EVALUATION_FAILED'
  | 'SEARCH_PROVIDER_FAILED'
  | 'UNKNOWN';
```

`modelClient.ts` 的 `buildApiError`（当前 414-417 行）按 HTTP 状态映射：

| 状态 | code | retryable |
|---|---|---|
| 401 | `CONFIG_MISSING` | false |
| 402 / 403 | `MODEL_QUOTA_EXHAUSTED` | false |
| 429 | `RATE_LIMITED` | true |
| ≥500 / 超时 / 网络异常 | `MODEL_UNAVAILABLE` | true |
| 其他 | `UNKNOWN` | false |

`route.ts:327-332` 的 `recoverable` 不再由 code 反推，改为透传
`AgentRunError` 携带的 `retryable`（`AgentRunError` 需保留原始 `AgentError.retryable`）。
`lib/api.ts` 与 UI 依据该字段决定是否渲染重试入口（R2.2）。

### D4 追问选项：optionId 协议

#### 类型变更

```ts
// lib/agent/types.ts
export interface PendingQuestionOption {
  id: string;      // 稳定语义 id，参与协议
  label: string;   // 纯展示文案，不参与任何判断
}

export interface PendingQuestion {
  reason?: string;
  question: string;
  options?: PendingQuestionOption[];
  allowFreeText: boolean;
  optionEffects?: Record<string, ClarificationEffect>; // key = option.id
}
```

内置选项 id 枚举（`lib/agent/clarificationOptions.ts`，新增）：

| id | 含义 | effect |
|---|---|---|
| `authorize_fallback_primary` | 开放推荐 | `buildFallbackPrimaryEffect()` |
| `authorize_category_broaden` | 放宽到相邻品类 | `buildBroadenEffect(goal)` |
| `expand_distance` | 扩大距离范围 | 距离授权 + `setDistanceMaxMeters` |
| `change_target` | 换个类型（仅提示用户改用自由文本） | 无 effect |
| `retry_turn` | 原样重跑本轮 | 无 effect，见 D4.3 |

`policy.ts` 中 `buildNoPrimaryQuestion` / `buildPostAuthorizationNoPrimaryQuestion`
改为产出上述 id，文案仅作为 label。

#### D4.1 模型产出的选项由后端分配 id

Supervisor 可以自行生成追问选项（`supervisor.ts:70` 规则 7a）。模型只输出
`{label, effect}`，**id 一律由后端分配**（`opt_1..n`），避免模型编造不稳定 id。
`clarificationNeedToPendingQuestion`（`supervisor.ts:363-377`）与
`PendingQuestionSchema` 负责这层转换。

#### D4.2 客户端回传 id

`POST /api/agent/chat` 请求体：

```ts
{
  message?: string;      // 自由文本；与 optionId 二选一，至少其一
  optionId?: string;     // 点击选项时回传
  sessionId?: string;
  location: Location;
  ...
}
```

服务端处理顺序：

1. `optionId` 存在 → 从 `session.pendingQuestion.optionEffects[optionId]` 取 effect，
   直接构造 `GoalPatch` 应用到当前 goal，**完全不调用模型**；
   会话消息记录写入该选项的 label（保证 messages 可读）。
   id 不存在于当前 pendingQuestion → 400，客户端提示"该选项已失效，请重新描述需求"。
2. 仅有 `message` → 走 Supervisor 做意图理解（R4.5）。

`supervisor.ts:233-254` 的 `deterministicClarificationAnswer` 改为按 id 查表，
删除全部字符串匹配；`applySupervisorClarifyingAnswer`（`supervisor.ts:336-361`）同理。

#### D4.3 `retry_turn` 的语义

不再把「重试」当成一句话喂给模型。`retry_turn` 表示：沿用当前 `session.goal` 与
`session.attempts` 原样重跑一轮，`conversationMode` 恒为 `continue_current_goal`，
不触发任何 reset。这直接消除了实测中「回答重试 → goal.rawQuery 变成『重试』」的问题。

#### D4.4 前端改动

- `components/LoadingSteps.tsx`：删除第 246-254 行硬编码的「你推荐」按钮；选项按钮
  遍历 `question.options` 渲染 `label`，`onClick` 回传 `option.id`。
- `hooks/useRestaurantSearch.ts`：删除第 178-195 行的选项改写与
  `allowFreeText: false`；`answerQuestion` 签名改为
  `(answer: { optionId: string } | { text: string })`。
- `questionCountRef` 保留，但仅用于展示辅助提示（"已经问了几轮，可以换个说法或重新
  开始"）并提供「重新开始」入口（本地清 sessionId），不再干预 options（R5.3）。
- `lib/api.ts`：`AgentQuestion.options` 类型同步为 `PendingQuestionOption[]`；
  `agentChat` 增加 `optionId` 参数。

### D5 循环终止不变量

`AgentSession` 新增两个字段（session `version` 3 → 4）：

```ts
lastQuestionFingerprint?: string;
consecutiveAskTurns: number;   // 默认 0
```

指纹定义：`normalize(question.question) + '|' + question.options?.map(o => o.id).sort().join(',')`。

Runtime 在**任何** `ask_user` 出口（`runtimeV3.ts:191-195` 与 `212-216`）之前统一
经过 `guardAgainstStalledClarification(context, question)`：

- 指纹与 `lastQuestionFingerprint` 相同，或 `consecutiveAskTurns >= 3`：
  - 有任意候选（含 backup）→ 转为 `finish`，`FinishReason` 新增 `CLARIFICATION_STALLED`；
  - 无候选 → 同样 `finish`（非 error），explanation 提示"没能理解你的需求，换个说法
    或直接说一个菜名"，并清空 `pendingQuestion`，避免会话死锁（R5.2）。
- 否则正常 ask，写入新指纹，`consecutiveAskTurns += 1`。
- 任何一次成功产出结果的轮次将 `consecutiveAskTurns` 归零。

配套：删除 `supervisor.ts:171-174` 的 throw。模型在 pendingQuestion 上下文返回新
question 属于合法输出，直接返回给 Runtime，由上述不变量兜底（R5.4）。仅当模型
既无 goal、无 patch、也无 question 时，才抛 `SUPERVISOR_UNAVAILABLE`。

### D6 单轮模型熔断

`AgentV3Context` 新增 `modelOutage?: AgentError`。`modelClient` 抛出的错误 code 属于
`MODEL_QUOTA_EXHAUSTED` / `CONFIG_MISSING`（不可恢复类）时，Runtime 记录到
`modelOutage`；此后本轮所有模型调用入口（Evaluation、KeywordExpansion、Replan）
在发起前检查该字段，非空则直接抛出已记录的错误，不再发请求。

配合 D1（Supervisor 失败即终止），模型全不可用时单轮模型调用次数为 1，
高德调用为 0，满足 R6。

### D7 模型配置

- `.env.example`：`OPENAI_MODEL=deepseek-v4-flash-0731`
- 代码默认值四处 `|| 'gpt-4o'` → `|| 'deepseek-v4-flash-0731'`：
  `supervisor.ts:35`、`supervisorPlanner.ts:48`、
  `subagents/evaluationAgent.ts:22`、`subagents/keywordExpansionAgent.ts:22`
- 文档同步：`README.md:813`、`CLAUDE.md:109`、`AGENTS.md:109`、
  `docs/Agent-Harness-优化技术方案-2026-08.md:458`
- 分级变量（`OPENAI_MODEL_SUPERVISOR` 等）行为不变。

## 4. 兼容与迁移

**旧会话的 pendingQuestion**（`options: string[]`，`optionEffects` 以文案为 key）：
`PendingQuestionSchema` 的 preprocess 增加升级逻辑——字符串选项升级为
`{ id: 'legacy:' + label, label }`，同时把 `optionEffects` 的 key 一并改写。
该兼容代码标注 `@deprecated`，会话 TTL（30 分钟）过后即可删除，计划下一个版本移除。

**session version**：3 → 4。`d1SessionStore` 读到 version < 4 的记录时按上述规则
升级后使用，不做破坏性丢弃。

## 5. 测试计划

### 单测（`__tests__/lib/agent/`）

1. Supervisor 抛 `MODEL_QUOTA_EXHAUSTED` → `runSearchAgentV3` 抛 `AgentRunError`，
   `searchPlaces` 零调用，且**不返回** runtimeState（保证会话不被写脏）。
2. 同上场景下，route 层 SSE 发 `error` 且 `recoverable: false`，会话内
   `goal.rawQuery`、`observations` 保持不变。
3. 评估全失败且无主推荐 → 抛 `EVALUATION_FAILED`；不产生 unverified 候选。
4. 评估部分失败但有主推荐 → 正常 `final`，`warnings` 非空，
   `finishReason = PARTIAL_EVALUATION_FAILURE`。
5. `evaluationFailed` 置位后 `decideNextAction` 不再返回 `search`。
6. `optionId = authorize_fallback_primary` → Supervisor mock 零调用，goal 获得
   `fallback_primary` 授权。
7. `optionId = retry_turn` → goal 与 attempts 不变，`conversationMode` 为
   `continue_current_goal`。
8. 未知 optionId → 400。
9. 旧格式 `options: string[]` 会话升级后仍能命中 effect。
10. 连续两轮产生相同指纹的追问 → 第二轮转 `CLARIFICATION_STALLED`，
    `pendingQuestion` 被清空。
11. 模型在 pendingQuestion 上下文返回**不同**的新追问 → 正常 ask，不抛
    `SUPERVISOR_UNAVAILABLE`。
12. 模型可用时自由文本「你推荐」→ Supervisor 产出 `allowBroaden` patch → 进入
    fallback 搜索（锁死"意图理解归模型"这条原则）。

模型分支用例需 `delete process.env.AGENT_DETERMINISTIC` 并 mock
`@/lib/withTimeout` 的 `fetchWithTimeout`，参考
`__tests__/lib/agent/supervisorPlanner.test.ts`。

### Eval（`npm run eval`）

新增两个 case：

- `model-unavailable`：桩模型全部返回 403。期望 `serialSearchSteps = 0`、
  `evaluationCalls = 0`、`modelCalls ≤ 1`、结果为 error。
- `clarification-convergence`：桩 Supervisor 持续返回同一追问。期望
  `askTurns ≤ 2`，最终 finishReason 为 `CLARIFICATION_STALLED`。

现有 case 的追问率与主推荐数会变化（删除降级搜索路径所致），PR 中附
`evals/baseline.json` 的 diff 并说明每一项变化的来源。

## 7. 回滚

PR-1 的风险集中在协议变更。回滚策略：

- 前后端同时回滚到上一个 tag（协议是成对的，不支持单侧回滚）。
- 会话 version 4 的记录被旧代码读到时，`options` 为对象数组会被旧
  `PendingQuestionOptionsSchema` 的 preprocess 降级成 label 数组（该分支已存在，
  见 `schemas/clarification.ts:35-43`），不会崩溃，最坏情况是选项失去 effect 而回落
  自由文本路径。
- D7 的模型配置为环境变量，可独立回滚。
