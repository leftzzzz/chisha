## 1. 背景

上一轮形态重构把动作决策权从模型收回到 `policy.ts`，指标达成（串行模型步 7→3，
顺序策略实现 3 份→1 份）。但**角色命名与实际结构脱节**的问题没有被处理：仓库里
自称"主 Agent"的模块不是主 Agent，真正的主 Agent 没有名字。

由此产生的后果是——编排逻辑没有归属，于是落在"当时手边那个文件"；而三个子 Agent
在多轮迭代中反向吸收了策略。这是本次要解决的问题。

### 1.1 现状盘点（2026-08-13，`lib/agent/` 共 9844 行）

`supervisor.ts:60` 的 prompt 首句是「你是 SupervisorPlannerAgent，是餐厅搜索**主
Agent**」。但它在一轮里只在 `runtimeV3.ts:158` 被调用一次，产出 goal 后即退场：

| 观察 | 证据 |
|---|---|
| 它的 `nextAction`（plan/ask_user/finish）无任何消费点 | 全仓 grep 只有 supervisor 自身、schema 定义与测试断言 |
| 它的 `question` 会被编排层整个替换 | `runtimeV3.ts:199` `groundQuestionInNearbyCategories` |
| 它算的 `conversationMode` 被重算一遍 | `supervisor.ts:184` 与 `runtimeV3.ts:801` 各一份 |
| 它接收的 `verdictSummary` 从未被传入 | `SearchSupervisorInput.verdictSummary` 无写入方 |

真正的编排者是 `runtimeV3.ts`（1827 行）+ `policy.ts`（813 行）。

## 2. 问题定义

**P1 主 Agent 身份错位。** 名为主 Agent 的模块实为一次性 NLU 子 Agent；它输出的
流程控制字段被静默丢弃。新人按文档理解架构会得到与代码相反的结论。

**P2 编排决策散落三处，已产生重复实现与漂移。**

| 决策 | 实际位置 |
|---|---|
| 下一步搜什么 / 够不够结束 | `policy.decideNextAction` |
| 追问选项 RETRY / CHANGE_TARGET 如何处理 | `runtimeV3.ts:695-721` |
| 连问三次是否收敛 | `runtimeV3.askOrConverge:1683` |
| 决策失败重试轮数 | `runtimeV3.ts:394` |
| 追问前是否探路 | `runtimeV3.ts:262-304` |
| 会话模式 / 状态是否清空 | supervisor 与 runtime 各一份 |

可验证的漂移：`primaryTargetSignature` 存在 **3 份**私有实现
（`goalVersion.ts:201`、`supervisor.ts:403`、`runtimeV3.ts:966`）；
`inferConversationMode` 存在 **2 份**且不等价（supervisor 多一条
「有 pendingQuestion → patch_current_goal」分支），其中 `runtimeV3.ts:817-827`
因 supervisor 的 normalize 恒填该字段而成为**死代码**。

这正是上一轮已经治过一次的病（「顺序策略实现份数 3→1」），换个字段又长了回来。

**P3 子 Agent 内含策略，且与既定原则冲突。**
`keywordExpansionAgent.ts:27-41` 内置两张硬编码词表——
`OPEN_EXPLORATION_FALLBACK_TARGETS`（小吃/中餐/快餐，无条件补入模型输出）与
`OPEN_EXPLORATION_DEMOTED_KEYWORDS`（8 个日料相关词强制降权），由
`stabilizeOpenExplorationTargets` 与模型输出混合后返回。这与
`CLAUDE.md` 中「不要新增任何用关键词表冒充模型判断的兜底路径」直接冲突。

更不一致的是失败处理：`keywordExpansionAgent.ts:136` 捕获异常后**静默**降级为本地
taxonomy，而 EvaluationAgent 失败会中止整轮。同一条原则在两个子 Agent 上执行相反，
且静默降级会让"模型不可用"这一事实对运维不可见——上一次线上事故正是这样被掩盖的。

**P4 子 Agent 被要求做超出其上下文范围的决策。**
EvaluationAgent 的职责是逐家判定，但 prompt 规则 5-7 要求它输出 `selectedIds` /
`candidateIds` 与排序倾向。这些 id 真实生效：`evaluator.ts:128` 给 `selectedIds`
中的餐厅 **+30 分**。同时 `finalGuard` 又独立重排一次，最终转盘顺序由谁决定是含糊的。

最硬的一处：该 Agent 被**分批**调用（`runBatchedEvaluationAgent`，每批 6 家，常规
12 家 = 2 批），每批只见 6 家却被要求"选出最好的"，随后
`mergeEvaluationOutputs` 将各批 `selectedIds` 直接 flat 去重。让只有局部视野的子
Agent 做全局选择，再机械合并，在语义上不成立。

**P5 子 Agent 在读编排层内部状态。**
`buildEvaluationModelInput` 传入**整个 `goal` 对象**，含 `authorizations`、
`broadenedTargets`、`goalVersion` 等与"这家店是否符合"无关的编排状态；
`keywordExpansionAgent` 收到 `authorizations` / `allowBroaden` / `attempts`，
并由 prompt 规则 1a/1b 要求它**自行判断当前处于哪个编排阶段**。

**P6 文档与代码不符。**
`CLAUDE.md` 称「模型只在三处介入」，实际有四处
（`grep agentName:`：SupervisorPlanner / SearchReplan / Evaluation / KeywordExpansion）。
`supervisorPlanner.ts` 已退化为转发层（一行转发 + `runSearchReplan` + 大量
re-export），使依赖图上看不出 runtime 依赖 supervisor。
`understandSearchGoal`（`supervisor.ts:281`）已无调用点。

## 3. 设计原则

### 3.1 编排者是代码，不是模型

上一轮重构刚把决策权从模型收回，有 eval 基线为证。**本次不把控制权交回模型**——
目标是让"编排者"这一角色显式化并正名，而不是改变它的实现方式。

### 3.2 分层判据

任何一段新代码用这一条即可定位归属：

| 特征 | 归属 |
|---|---|
| 需要理解自然语言或语义 | 子 Agent（`subagents/`） |
| 需要枚举状态做选择 | 编排层决策（`policy`） |
| 需要发请求、发事件、改状态 | 编排层执行（`runtime`） |
| 同样输入永远同样输出且不含语义 | 确定性规则库 |

### 3.3 依赖单向

编排层 → 子 Agent、编排层 → 规则库、编排层 → 工具层，**只允许这三条**。
子 Agent 之间不得互相引用，也不得引用编排层。该约束须写成可执行测试，不止写进文档。

### 3.4 子 Agent 的输入契约可用一句话描述，且不提及 loop

「给定目标与这批餐厅事实，逐家判定是否满足」合格；
「给定 authorizations 与 attempts，生成探索词并注意开放推荐时要多样」不合格。

## 4. 需求条目

### R1 确立唯一编排者（对应 P1、P6）

- R1.1 存在一个明确的编排层，包含决策与执行两部分；除它之外没有模块决定流程。
- R1.2 现 Supervisor 降级为与其他子 Agent 平级的目标理解 Agent，名称、prompt 与
  文件位置一致反映该定位。
- R1.3 删除子 Agent 输出中的流程控制字段（`nextAction`），包括 schema、prompt 与
  测试断言。
- R1.4 `supervisorPlanner.ts` 转发层删除，replan 成为独立子 Agent。
- R1.5 删除无调用点的导出与从未被写入的输入字段。

**验收标准**
- [ ] 全仓不存在自称"主 Agent"但不控制流程的模块。
- [ ] 模型调用点数量与文档描述一致，且每个调用点都能说明"它只做哪一件事"。
- [ ] 存在一条 grep 可验证：子 Agent 输出中无流程控制字段。

### R2 编排决策收敛到单一模块（对应 P2）

- R2.1 P2 表格中列出的六类决策全部由决策模块给出；执行模块只执行返回的决策。
- R2.2 决策模块保持纯函数：不发起 I/O、不调用模型、不修改传入状态。
- R2.3 判断"用户这句话与上文的关系"属于语义判断，保留在子 Agent；
  判断"因此要不要清空搜索状态"属于编排决策，归决策模块。二者不得混在一处。

**验收标准**
- [ ] 执行模块中不存在 `if` 分支决定下一步动作类型。
- [ ] 决策模块的全部导出函数都可在无 mock 条件下单测。

### R3 消除重复实现（对应 P2）

- R3.1 `primaryTargetSignature` 全仓唯一实现。
- R3.2 `conversationMode` 的推导逻辑唯一，删除死代码路径。
- R3.3 阈值、上限、指纹规则等常量保持单一来源。

**验收标准**
- [ ] `grep -c "function primaryTargetSignature"` 结果为 1。
- [ ] 不存在两处实现同一判断且结论可能不同的代码。

### R4 子 Agent 输入契约收窄（对应 P5）

- R4.1 每个子 Agent 定义显式的任务输入类型，不再传入完整 `UserGoal` 或运行时状态。
- R4.2 编排层状态（`authorizations`、`allowBroaden`、`attempts`、`goalVersion`、
  `relatedTargets` / `broadenedTargets`）不得出现在子 Agent 输入中。
- R4.3 需要子 Agent 区分场景时，由编排层判定后以显式参数告知，不让子 Agent
  从编排状态自行推断阶段。

**验收标准**
- [ ] 存在测试断言各子 Agent 的模型输入不含 R4.2 列出的字段。
- [ ] KeywordExpansion 的 prompt 中不再有"根据 X 判断当前处于哪种情况"式规则。

### R5 EvaluationAgent 只做逐家判定（对应 P4）

- R5.1 移除其 `selectedIds` / `candidateIds` 输出与相关 prompt 规则。
- R5.2 候选选择与排序完全由确定性规则决定。
- R5.3 移除评分中基于模型选择结果的加分项。

**验收标准**
- [ ] 分批调用不再产生需要跨批合并的选择结果。
- [ ] 相同输入下候选顺序完全可复现（不依赖模型输出顺序）。
- [ ] 附 eval 基线 diff，说明转盘顺序变化。

### R6 KeywordExpansion 去硬编码并对齐失败原则（对应 P3）

- R6.1 删除 `OPEN_EXPLORATION_FALLBACK_TARGETS` 与
  `OPEN_EXPLORATION_DEMOTED_KEYWORDS` 两张词表及其混合逻辑。
- R6.2 生产环境下模型调用失败不再静默降级；失败以结构化错误暴露。
- R6.3 确定性词表（同义词归一等属于规则库的部分）保留，但只在显式的确定性开关
  下使用，不作为模型失败后的隐式替身。

**验收标准**
- [ ] 模型不可用时，开放推荐路径以明确错误结束，日志与 trace 可见失败原因。
- [ ] 代码中不存在"无语义依据地指定搜索方向"的常量数组。

### R7 文档与代码一致（对应 P6）

- R7.1 `CLAUDE.md` / `AGENTS.md` 的模块清单、模型介入点数量、分层判据与代码一致。
- R7.2 新增架构图与分层判据，作为后续改动的归属依据。

**验收标准**
- [ ] 按文档描述能画出与实际调用图一致的结构。
- [ ] 文档中每个模块职责描述都能在代码中找到对应边界。

## 5. 非目标

- **不把动作决策权交回模型**——这会回退上一轮重构，串行模型步与成本将回升。
- 不改 SSE 事件契约与前端状态机。
- 不改 `FinalGuard` 的准入语义与授权 scope 模型。
- 不改会话 schema 与 D1 version。
- 不改评分算法的距离分档与匹配加分（R5.3 移除的仅是模型选择加分项）。
- 不引入多供应商切换、上下文压缩、模型输出缓存。

## 7. 风险

- **搬运范围大**：阶段 1-2 涉及大量 import 变更。缓解：这两个阶段要求 eval 基线
  diff 为空，任何非零 diff 都说明搬错了。
- **R5 改变用户可见排序**：转盘顺序会变化。这是明确取舍——用可复现的确定性排序，
  换掉一个由局部视野模型给出、再被机械合并的选择结果。
- **R6 降低可用性**：模型不可用时开放推荐将直接报错而非给出兜底方向。与既定
  原则一一致，属于有意为之。
- **依赖方向测试可能与现有引用冲突**：`policy.ts` 现引用
  `finalGuard.isPrimaryRecommendationAllowed`。需在技术方案中确认规则库可被决策层
  单向依赖，否则该测试无法通过。
