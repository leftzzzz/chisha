## 2. 设计决策

### D1 目录重排与文件拆分

```
lib/agent/
  orchestrator/
    policy.ts          ← 现 policy.ts + runtime 外移的五处决策
    runtime.ts         ← 现 runtimeV3.ts 瘦身
  subagents/
    goalUnderstandingAgent.ts  ← 现 supervisor.ts 的模型部分
    keywordExpansionAgent.ts
    evaluationAgent.ts
    replanAgent.ts             ← 现 supervisorPlanner.ts 的 runSearchReplan
  goal.ts              ← 现 supervisor.ts 的纯函数目标代数
  （其余规则库文件位置不变）
```

`supervisor.ts` 现有 1033 行中约 430 行（`:217-595` 与 `:640-690`）是与模型无关的
纯函数目标代数——`applyGoalPatch`、`normalizePendingAnswerPatch`、
`applyClarificationOptionToGoal`、`goalPatchFromClarificationEffect`、
授权合并与各 `mergeXxx`。
它们被子 Agent 文件挟持，导致任何想复用目标合并的地方都得 import 一个模型 Agent。
拆到 `goal.ts` 后，`applyGoalPatch` 归规则库，供编排层直接调用。

`supervisorPlanner.ts` 整体删除。它的三类内容分别去向：

| 内容 | 去向 |
|---|---|
| `runSupervisorPlanner`（一行转发） | 删除，调用方直接用 `runGoalUnderstandingAgent` |
| `runSearchReplan` + prompt + schema | `subagents/replanAgent.ts` |
| `summarizeAction` / `createActionRecord` | `orchestrator/runtime.ts`（本就是执行层的事） |
| 全部 re-export | 删除，`route.ts:20` 改为直接 import `goal.ts` |

`understandSearchGoal`（`supervisor.ts:281`）与 `SearchSupervisorInput.verdictSummary`
无调用点/无写入方，一并删除。

### D2 五处决策外移

| 决策 | 现位置 | 新 API |
|---|---|---|
| optionId 入口分派 | `runtimeV3.ts:675-747` | `decideTurnEntry()` |
| 会话模式 → 状态重置 | `runtimeV3.ts:801-874` + `supervisor.ts:184` | `decideContextReset()` |
| 追问前探路时机 | `runtimeV3.ts:262-304` | `decideScouting()` |
| 追问收敛 | `runtimeV3.ts:1683-1713` | `decideAskOrConverge()` |
| 决策重试轮数 | `runtimeV3.ts:394` `MAX_DECISION_ROUNDS` | `decideNextAction` 内部消解 |

保持 policy 纯函数的关键是**只返回决策数据，不做 I/O**：

```ts
export type TurnEntryDecision =
  | { kind: 'apply_effect'; goal: UserGoal; conversationMode: ConversationMode }
  | { kind: 'rerun_current_goal'; goal: UserGoal }
  | { kind: 'ask'; question: PendingQuestion }
  | { kind: 'understand'; message: string };   // runtime 据此调子 Agent

export type ScoutDecision =
  | { kind: 'skip' }
  | { kind: 'scout'; plan: SearchPlan };       // runtime 负责真正发这次搜索

export type AskDecision =
  | { kind: 'ask'; question: PendingQuestion }
  | { kind: 'converge'; reason: 'CLARIFICATION_STALLED' };
```

`decideScouting` 只回答"要不要探、用哪个计划探"；发请求、把结果交给
`summarizeNearbyCategories`、拿回问题，仍由 runtime 完成。这条边界保证 policy
可在无 mock 条件下单测（R2.2）。

### D3 conversationMode 的归属修正

需求 R2.3 的依据在此展开。`conversationMode` 混了两件事：

- **「用户这句话与上文是什么关系」**——需要理解自然语言（"换成日料"是修改还是
  新需求，签名比较看不出来）。按分层判据归**子 Agent**。
- **「因此要不要清空 attempts / candidates」**——枚举状态做选择。归**编排层**。

因此：

- 保留 `goalUnderstandingAgent` 输出 `conversationMode`（它是语义判断）；
- 删除 `runtimeV3.ts:801-828` 的 `inferRuntimeConversationMode`。该函数在
  `output.conversationMode` 分支之后的代码（817-827 行）本就是死代码——
  `normalizeSupervisorOutput` 恒填该字段；
- `deriveSearchStateResetPlan`（`runtimeV3.ts:830-874`）移入
  `policy.decideContextReset(mode, invalidationPlan)`。

`primaryTargetSignature` 只保留 `goalVersion.ts:201` 一份并导出，
`goal.ts` 与 `policy.ts` 改为 import（R3.1）。

`nextAction` 从 `SUPERVISOR_FUNCTION` schema、`SearchSupervisorOutputSchema`、
`normalizeSupervisorOutput` 与全部测试断言中删除（R1.3）。

### D4 子 Agent 输入契约

每个子 Agent 定义显式任务类型，不再接收 `UserGoal` 整体。

**EvaluationAgent**

```ts
export interface EvaluationTask {
  /** 只含可验证的目标部分 */
  target: {
    requestedItems: RequestedItem[];
    acceptableCategories: GoalCategory[];
    hardConstraints: Constraint[];
    softPreferences: SoftPreference[];
    exclusions: string[];
  };
  searchedKeywords: string[];      // 取代整个 plan
  restaurants: RestaurantFact[];
  targetCount: number;
}
```

移除：`authorizations`、`allowBroaden`、`goalVersion`、`rawQuery`、
`clarificationNeeded`、`relatedTargets` / `broadenedTargets`、
`plan.allowedForPrimary` / `planId` / `radiusMeters`。
`existingCandidates` 保留——同批去重需要它，且属于该 Agent 的判定输入。

**KeywordExpansionAgent**

```ts
export interface KeywordExpansionTask {
  /** 编排层判定后告知，取代 prompt 规则 1a/1b 让模型自行推断阶段 */
  mode: 'expand_targets' | 'open_exploration';
  targets: string[];               // mode=expand_targets 时非空
  openContext?: {                  // 仅 open_exploration
    rawQuery: string;
    softPreferences: SoftPreference[];
    preferenceSummary?: UserPreferenceSummary;
  };
  excluded: string[];
  alreadyTried: string[];
}
```

移除：`authorizations`、`allowBroaden`、`attempts`（改为已归一的
`alreadyTried`）。prompt 规则 1/1a/1b/4/11 相应重写为按 `mode` 分述，
不再让模型判断"当前是否已获授权"。

**GoalUnderstandingAgent**：移除 `attempts` 与 `verdictSummary`
（理解用户话不需要搜索历史；后者本就无人写入）。其余保留——对话上下文正是它的职责。

**ReplanAgent**：`attempts` 全量改为
`{ triedKeywords, triedIntents, foundCounts }` 摘要。

### D5 EvaluationAgent 只做逐家判定

- `EVALUATION_FUNCTION` 删除 `selectedIds` / `candidateIds` 属性与 `required` 项；
- SYSTEM_PROMPT 删除规则 5、6、7（选择与排序），保留 1-4（判定与证据）；
- `evaluator.calculateScore`（`evaluator.ts:119-153`）删除 selectedIds +30 /
  candidateIds +10 两个加分项及相关参数；
- `guards.applyVerdictGuard` 中 `orderAllowedIds` 的 `requestedIds` 恒传空数组
  后可简化为纯排序函数。

**这条改动的成本比预想低**：`guards.ts:170-189` 的 `orderAllowedIds` 已有确定性
兜底——模型给的 id 只填充 `direct` 部分，其余由 `fill` 按 `compareVerdicts` 排序
补齐。移除模型选择等价于 `direct` 恒空、全部走 `fill`，排序逻辑本就存在，无需新写。

行为影响：转盘顺序改由 `confidence` + `matchedItems` + `matchedCategories` +
`distance` + `searchIntent` 决定，完全可复现。必须附 eval 基线 diff。

### D6 KeywordExpansion 去硬编码与失败原则对齐

删除 `keywordExpansionAgent.ts:27-41` 的两张词表与
`stabilizeOpenExplorationTargets` / `isDemotedOpenExplorationKeyword`（269-312 行）。

失败处理需要区分两类"确定性路径"，这一点必须讲清楚，否则容易误伤：

| 路径 | 性质 | 处置 |
|---|---|---|
| `OPEN_EXPLORATION_FALLBACK_TARGETS` = [小吃, 中餐, 快餐] | **无语义依据地指定搜索方向**，是拿常量冒充判断 | 删除 |
| `OPEN_EXPLORATION_DEMOTED_KEYWORDS` = 8 个日料词 | 同上，且是针对特定品类的隐式偏见 | 删除 |
| `expandPoiSearchKeywords`（火锅→涮锅等同义词归一） | 确定性词表，属规则库，无语义推断 | 保留 |
| `AGENT_DETERMINISTIC=1` 走 taxonomy | 测试开关，显式 | 保留 |
| 生产模型失败 → 静默转 taxonomy（`:136`） | 让"模型不可用"对运维不可见 | 删除，改抛错 |

即：删掉的是**隐式替身**，保留的是**显式的确定性规则**。原则一约束的是前者。

`runKeywordExpansionAgent` 失败改为抛 `AgentError(..., 'MODEL_UNAVAILABLE'|上游码, retryable)`，
与 EvaluationAgent 一致。`decideNextAction` 已有 `evaluationFailed` 分支，
新增对称的 `keywordExpansionFailed` 处理：**已有 initial targets 时不阻塞本轮**
（首批搜索不依赖联想词），仅在开放推荐这种"联想词就是唯一方向来源"的场景下 abort。

### 7.1 与方案不一致的四处

**① D3/R3.1 的前提被证伪：`primaryTargetSignature` 的三份实现不是同一个判断。**
`goalVersion.ts` 那份是**分字段**签名，`supervisor.ts` 与 `runtimeV3.ts` 那两份是
**合并集合**签名——同一个词在 `requestedItems` 与 `primaryKeywords` 之间挪动时，
前者判"变了"、后者判"没变"。按方案强行统一会静默改变"候选是否作废"的行为。

实际做法：删掉 runtime 里的死代码副本；剩下两份按语义分别命名为
`primaryTargetFieldSignature`（作废候选用，保留分字段语义）与
`primaryTargetSetSignature`（会话模式用，只关心目标词整体变没变），
并在两处注释里写明差异与各自用途。

教训：**"有 N 份实现"不等于"有 N 份重复"。** 合并前必须逐份比对语义，
否则去重本身就是一次静默的行为变更。

**② D3 对 `conversationMode` 的处理比方案更细。**
方案写"删除 runtime 那份重复推导"，实现时进一步区分：runtime 的
`inferRuntimeConversationMode` 在 `output.conversationMode` 分支之后的代码
（817-827 行）**从未执行过**——`normalizeSupervisorOutput` 恒填该字段。
所以删掉的是死代码，剩下的两个分支（无历史目标 / 有 patch）保留为
`resolveConversationMode`，因为它们是编排层能独立判定的边界情况。

**③ D2 的 `MAX_DECISION_ROUNDS` 没有简单"内部消解"。**
方案说让 `decideNextAction` 内部消解重试循环。实际做不到——把被拒计划记为
已尝试是**状态写入**，policy 是纯函数不能做。

实际做法：policy 在返回搜索决策前自己调 `validateSearchPlan`
（`partitionPlansByValidity`），并新增 `invalid_plans` 决策类型。一批全被拒时
不再"记为已尝试再重新决策"绕过去——那会把策略 bug 伪装成"这个词搜过了"——
而是以专门的决策类型报出来，runtime 按 error 级别上报后再决策一次。
runtime 保留的循环只服务于 `replan` 与 `invalid_plans` 这两个"先做点事再重问"
的分支，不再包含任何"下一步做什么"的判断。

**④ D5 的 eval 验证一开始是假的。**
阶段 4 首次跑 eval 得到"基线无变化"，但那不算证据：`evals/harness.ts` 的
evaluation 桩**仍在返回 `selectedIds`**，用旧契约掩盖了新契约的差异。
改掉桩之后重跑，仍是无变化——这才是真证据。

但 eval 只度量计数（搜索步数、评估调用数、追问率、主推荐数），**不度量转盘
顺序**。因此另加 `__tests__/lib/agent/evaluator.test.ts` 直接锁定"排序与模型
选择无关且可复现"。

教训：**改契约时必须同步改桩，否则评测会用旧行为掩盖新行为。**
这一条已写进 `docs/TESTING.md`。

### 7.3 仍然未决

**ReplanAgent 的去留。** 保留并搬到 `subagents/replanAgent.ts`——没有证据就删代码
比留着更糟。判断依据仍然缺失：`plannerModelCalls: 0` 不能当证据，因为
`evals/setup.js` 强制 `AGENT_DETERMINISTIC=1`，而 `runSearchReplan` 在该模式下
直接返回 `null`，模型根本不会被调到。要定去留得采生产 trace 统计 replan 分支的
实际命中率与后续转化。

**`runAgentTurn` 里还剩两个流程分支没外移。** 画架构图时暴露的：

```
if (clarifyingQuestion)            // 子 Agent 说要先追问 → ask
if (promotion.promotedCandidates)  // 放宽授权后已有候选转正 → finish
```

两者都只是**转发上游已经做出的判断**（子 Agent 的语义结论、broadenAdmission 的
准入结果），不像被外移的那五处那样自行在多个动作里选择，所以危害有限。但按
R2「执行模块中不存在 if 分支决定下一步动作类型」的字面要求，这一条并未完全成立
——需求文档的验收已相应改为"部分达成"。

没有一并外移的原因：`promoteAuthorizedBroadenedResults` 会**修改** context
（把候选转正），是执行动作不是纯判断；要让 policy 决定就得把它提到追问判断之前，
而那会让"本轮以追问结束"的场景也执行一次转正，改变持久化的会话状态。这个顺序
调整值得单独做一次并用 eval 的 multiturn 用例验证，不适合夹在文档修正里顺手改。

**`orchestrator/runtime.ts` 仍有 1727 行。** 外移五处决策只减了 100 行——大头是
搜索执行、评估批处理与 trace 三块。可进一步拆分，不在本次范围内。

**规则库仍平铺在 `lib/agent/` 根目录。** 靠 `layering.test.ts` 约束方向而非目录
结构。若后续觉得根目录文件过多，可作为独立小改动跟进。
