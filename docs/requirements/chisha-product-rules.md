# ChiSha 业务规则与产品边界

> 状态：当前产品规则。本文收敛跨功能的用户流程和产品行为；Agent 搜索语义、候选证据与最终发布准入分别由关联需求文档维护。

## 权威分工

- 本文负责输入、位置、转盘、历史和用户交互的跨功能业务规则。
- [Restaurant Search Agent Requirements](./restaurant-search-agent.md) 负责自然语言搜索、目标关系、授权、证据和模型不可用时的产品边界。
- [最终推荐发布边界](./final-recommendation-publication.md) 负责主推荐、候补分区、顺序保真和 FinalGuard 发布规则。
- `docs/specs/` 负责当前实现必须满足的工程契约；`docs/technical/` 负责架构方案和技术理由。

## 用户输入

- 用户通过自然语言表达想吃的方向、限制和偏好；输入不能为空。当前 Agent 聊天入口接受 1 至 500 个字符的消息。
- 搜索必须绑定位置。位置可以来自浏览器定位，也可以由用户输入地址并完成地理编码；没有有效位置时不能开始附近餐厅搜索。
- 位置切换后，新的搜索以新位置为准；历史记录或分享内容恢复出的转盘可以展示，但不能把旧位置默认为当前定位。
- 用户原始表达和其中的限制、排除项、修饰词属于本次目标的一部分，不因内部分类、关键词表或 Provider 字段而丢失。

## 搜索与对话

- 系统优先完成用户明确表达的目标；目标不清楚时可以追问，追问结果必须继续保持在同一会话上下文中。
- 追问选项的稳定 `id` 是协议字段，`label` 只负责展示。点击选项按后端定义的状态效果执行，不把展示文案当作新的自由文本语义输入。
- 用户可以用自由文本回答追问；自由文本必须交给负责目标理解的模型处理，代码不得用固定词表猜测其意图。
- 模型或外部数据不可用时，系统必须显式失败或标记未知，不得用本地菜名、菜系或品牌词表伪造模型结论。具体错误码、证据状态和候选处理见 Agent Requirements。
- 搜索命中、地点事实和目标证据必须保持可区分；候选数量不足不能成为提升证据等级或放宽主推荐条件的理由。

## 转盘与候补

- 转盘最多包含 8 个选项；餐厅和用户添加的自定义文字选项共享这一上限。
- 转盘至少有 3 个选项才允许开始转动。搜索结果少于该数量时，界面保留真实数量并引导用户重新搜索或添加选项，不伪造空餐厅或自动补位。
- 后端返回的主推荐与候补保持分区。候补不能自动进入转盘，只有用户明确执行“加入转盘”后才能加入，并且仍受转盘容量和去重规则约束。
- 用户可以移除转盘选项、恢复已移除餐厅、把转盘餐厅移入候补池，或添加自定义文字选项。删除导致选项少于 3 个时，转盘不能继续转动。
- 展示层不得为了凑满转盘而重新选择、补位、重排或提升候补证据；详细发布边界以 [最终推荐发布边界](./final-recommendation-publication.md) 为准。

## 历史记录

- 用户完成一次转盘选择后，系统自动保存本次查询、位置、参与选项和选中结果到浏览器本地历史；不依赖服务端历史才能查看已有记录。
- 历史记录按时间倒序保存，最多保留 100 条；超过上限时删除最早记录。浏览器存储不可用时不得伪称已经持久化成功。
- 同一查询、同一坐标且间隔不超过 30 分钟的“再来一次”属于同一搜索会话，只保留该会话最后一条记录。
- 历史页支持查看、按查询或餐厅信息搜索、删除单条、清空、导入、导出和重新使用记录；重新使用记录不能自动恢复已过期的 Agent 会话。
- 随机抽中的结果只表示本次转盘结果，不表示用户去过、喜欢或主动接受。历史页可以展示
  抽中次数，但不得把它命名为“最常去”或“最喜欢”。
- 历史中提炼的偏好只能影响后续默认搜索倾向，不能覆盖本次用户明确提出的硬约束、排除项
  或位置；只有显式反馈或用户主动操作才可以形成强偏好。

## 发布与失败

- 正常完成、部分结果、预算耗尽或追问收敛，只要准备返回主推荐，都必须遵守同一套最终发布边界。
- 没有合格主推荐时，产品显示真实的未满足约束、证据不足或服务失败原因；不能通过装配器生成“看起来满足”的推荐理由。
- 用户主动从候补区加入餐厅是一次明确的产品选择，不等同于系统自动把候补提升为主推荐。

## 非目标

- 不承诺仅凭地图 POI 数据验证任意餐厅的实时完整菜单。
- 不建立跨 Provider 的通用餐饮语义分类表来替代开放世界目标理解。
- 不把固定的餐厅数量、模型调用次数或固定搜索动作序列作为产品质量目标。
