# Restaurant Search Agent Requirements

## 目标

ChiSha 必须能够理解开放世界的自然语言餐饮需求，在用户授权范围内寻找餐饮场所，
并把“搜索相关”与“有证据满足目标”明确区分。系统不能依赖不断增长的菜品、菜系或
关键词特判来维持正确性。

## 用户需求

1. 用户输入“寿司”“柠檬茶”“附近便宜且不辣的店”等自然语言时，系统保留完整表达，
   不因内部分类或已知词表丢失修饰词。
2. 系统需要扩大或替代目标时，必须说明新搜索与原目标的关系，并获得已有授权或先
   追问用户。
3. 用户能区分：有证据满足目标、证据矛盾、数据不足但可能相关。
4. 系统不能因为推荐数量不足，把未核实候选描述为已经满足目标。
5. 简单需求应直接、低延迟地完成；复杂且可并行的任务可以委派 specialized
   subagents，但多 Agent 不能成为固定仪式。
6. 模型或外部数据不可用时，系统显式失败或说明未知，不用本地语义规则伪造结论。

## 产品决策

- 地点搜索以自然语言 query 为主，不向 Agent 暴露高德或其他 Provider 的分类目录、
  category id/ref 或 typecode 选择流程。
- Provider 固定餐饮范围只用于排除非餐饮场所，不代表具体菜品或菜系。
- 搜索命中、地点名称、Provider category、菜单/商家资料分别作为可追溯事实保存，
  不混为一个置信度。
- `broader/alternative` 是用户可感知的范围变化，不是 Adapter 或 Runtime 的隐式兜底。
- 主推荐要求满足全部硬约束且目标证据为 `supported`；`unknown` 只能进入明确标注的
  不确定候补。

## 验收标准

- 对未出现在任何生产词表中的新菜品，系统仍能原样发起自然语言地点搜索。
- `寿司` 搜索不会在 Adapter 中被静默替换为 `日本料理`，也不会向 Agent 请求
  `050202`；若 Lead Agent 后续搜索“日本料理”，trace 标记为 `broader` 并包含授权。
- `柠檬茶`、`柠檬水` 等输入不会触发新增菜品到 Provider code 的映射规则。
- 仅有“POI 被归类为日本料理”的候选不能据此判定“提供寿司”。
- 删除菜单或商家证据后，候选资格从 `supported` 降为 `unknown`，不会继续留在主推荐。
- Lead-only 和 Lead + subagents 在真实模型 eval 中分别报告正确率、证据覆盖、成本、
  延迟和失败率；没有可测收益的委派默认关闭。
- Runtime 能追踪 parent-child run，并对超时、重试、取消和恢复保持幂等。

## 非目标

- 不承诺仅凭高德/OSM POI 数据验证任意餐厅的实时完整菜单。
- 不构建跨 Provider 的通用餐饮语义 taxonomy。
- 不以固定模型调用次数或固定 action 序列作为产品质量目标。
