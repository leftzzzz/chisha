# 最终推荐发布边界需求

## 目标

ChiSha 对外发布的主推荐必须与搜索过程中已经记录的目标、授权、硬约束和证据一致。
当前 workflow 提议结束后，下游组件只能阻止不合格结果，不能为了凑满转盘而
重新选择、补位或提升证据等级。

本需求关注“哪些结果可以离开搜索 workflow 并进入产品界面”，不改变开放世界搜索目标
和当前模型角色、Policy、Runtime 的责任边界。

## 用户需求

1. 用户看到的主推荐都已经通过当前目标、位置、硬约束、搜索授权和候选证据校验。
2. 证据不足但可能相关的餐厅只能出现在明确标注的候补区，不能自动进入转盘。
3. 如果部分提议结果不合格，系统宁可少给，也不能静默换成上游 workflow 没有选择的
   餐厅。
4. 最终展示顺序应保留上游提议顺序；下游不得再按分数、距离、品牌或随机规则重排。
5. 用户应能看到结果减少、证据不足或授权不足的真实原因，而不是由装配器推测出的搜索
   过程说明。
6. 用户可以主动把候补加入转盘，但系统不能代表用户执行该选择。

## 产品决策

- `FinalGuard` 是所有主推荐发布路径不可绕过的最终准入边界。
- `FinalGuard` 只允许删除、降级或分区；不得生成新候选、自动补位、重新排序或修改
  evidence verdict。
- `passed`、`primaryEligible`、目标与位置新鲜、无硬约束失败且搜索 scope 已授权，是主
  推荐的共同必要条件。FinalGuard 还必须根据当前餐厅事实重新计算距离、预算和营业状态
  等确定性硬约束，不能只信任候选携带的旧 `hardFailures`。存在必选菜品时，还必须有
  对应菜品证据，或满足已明确授权的放宽契约。
- `unverified` 可以作为不确定候补；`failed`、过期或明确违反硬约束的候选不对外发布。
- 候补不足以让转盘可转时，界面保持真实数量并提供候补区，不自动补足最低格数。
- `ResultAssembler` 只把已经通过 FinalGuard 的领域结果映射为 API/UI 数据；不得调用
  FinalGuard，也不得推导新的选择、排名、搜索策略或证据结论。

## 验收标准

- 三个 `unverified` 品类兼容候选不能因为主推荐为空而进入 `restaurants`；它们只能进入
  `candidates`，并带有证据不足提示。
- 删除一个候选的支持证据后，该候选从主推荐降为候补，不会由下一个未选择候选自动
  顶替。
- 提议顺序为 `B, A, C` 时，若 `A` 不合格，最终主推荐顺序为 `B, C`，而不是重新按
  score 或 distance 排序。
- 未观察到的 candidate id、重复 id、过期候选和硬约束失败候选产生可追踪的 FinalGuard
  verdict，且不会进入主推荐。
- “2 公里内”候选即使错误地携带空 `hardFailures`，实际距离超过 2 公里仍会被删除；
  严格距离缺少事实字段时只能降为候补。
- 未授权的 `broader/alternative` 候选不能进入主推荐，但满足候补基本安全条件时可以在
  候补区明确标注。
- 正常完成、预算耗尽、追问前的部分结果和防止重复追问的收敛路径，只要返回主推荐，
  都必须经过同一 FinalGuard。
- `ResultAssembler` 的单测能够在不调用 FinalGuard 的情况下，用已经 guarded 的输入完成
  映射。
- 前端 reducer 不会把 `candidates` 自动移动到 `restaurants`，也不会把超出展示上限的
  `restaurants` 重标为候补；同一品牌的不同门店不会被展示层静默折叠。
- workflow eval 的证据删除、工具结果重排和未授权 broaden 用例保持上述不变量。

## 当前架构边界

当前 `runSearchAgentV3` 的确定性 workflow 是已接受的生产架构：

- Runtime 显式调用 FinalGuard，再调用 ResultAssembler；
- 当前 workflow 对不合格提议执行单调降级，并按现有追问/安全结束逻辑收敛；
- 不为模拟 Lead Agent model-tool loop 增加伪 observation 重试；
- 如果未来重新评估 Agent 架构，必须通过独立技术决策定义 FinalGuard 如何与新 loop 集成。

## 非目标

- 不实现 `RestaurantSearchLeadAgent`、统一 `Agent` tool 或 subagent lifecycle；当前产品
  架构不要求这些能力。
- 不要求为凑满转盘而放宽主推荐证据标准。
- 不把随机选择、品牌多样性或推荐排序重新实现为 FinalGuard 规则。
- 不改变用户主动从候补区添加餐厅的能力。
