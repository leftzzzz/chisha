# Agent 架构改进需求

> 状态：正确性修复已开始实施，尚未整体验收；需业务数据支持的新产品决策仍待评审。
> 配套方案见 [Agent 架构审查与改进技术方案](../technical/agent-architecture-review.md)。
> 当前强制边界仍以 [Restaurant Search Agent Spec](../specs/restaurant-search-agent.md)
> 和 [Application Behavior Spec](../specs/application-behavior.md) 为准。

## 目标

ChiSha 的 Restaurant Search Agent 需要在保证目标保真、证据边界、硬约束和授权边界的前提下，
更快把用户从“想吃点什么”带到“能放心选择”的结果。当前确定性 multi-model workflow 仍然是
已接受的架构方向；本文定义它必须补齐的业务能力，不引入自主多 Agent 或 model-tool loop。

本文来自 2026-09-17 的仓库级 Agent 架构审查。它区分两类内容：

- 必须修复的正确性与契约问题；
- 需要用业务数据验证后再扩大投入的体验、召回和偏好问题。

本文是改进项目的验收清单，不是另一份运行规范。既有产品承诺见
[Restaurant Search Agent Requirements](./restaurant-search-agent.md) 和
[最终推荐发布边界](./final-recommendation-publication.md)。新增排序、反馈和部分成功策略在
评审接受时，应同步相关 Spec；实施进度见下文，不代表已部署或线上效果已验证。

## 用户需求

1. 用户表达“羊肉火锅”“无糖柠檬茶”“不辣的川菜”等需求时，系统保留原始目标、修饰词和
   显式约束。内部检索改写只能作为可追踪的新 action，不能静默改变语义关系。
2. 模型输出的结构化数据可以被校验、修复或拒绝，但不能因为一条格式错误的硬约束导致其他
   正确硬约束丢失。
3. 用户能理解推荐结果的证据边界：
   - 满足当前证据、硬约束、授权和新鲜度准入要求的餐厅，才可以进入主推荐；名称或分类
     不能单独证明具体菜品、无糖选项或实时供应；
   - 数据缺失但可能相关时，只能进入明确标注的不确定候补；
   - 存在明确冲突、过期、未授权或硬约束失败时，不能进入主推荐。
4. 系统不能用“看起来相关”替代“全部必选目标已支持”。当无法验证某项需求时，宁可少推荐，
   也不能增强满足性表述。
5. 推荐排序应区分“是否合格”与“合格后哪个更值得考虑”。距离只是约束和便利性因素，不是
   推荐效用的全部。
6. 搜索失败时，系统应区分没搜到、搜到但冲突、证据不足、未授权、预算耗尽和系统故障，
   并提出最可能改变结果的一个追问，而不是默认询问扩大范围。
7. 用户应能在结果中看到证据不足、候补、授权范围和未满足约束的真实原因。
8. 随机转盘结果不能自动被解释为强偏好。只有显式反馈或用户主动确认的选择才能形成
   更强的偏好信号。
9. 模型、地图或评估服务失败时，系统显式失败、保留可恢复状态或明确说明部分失败，不用
   静默降级伪造结果。

## 改进需求

### P1：正确性与契约一致

1. UserGoal 的原始表达、requestedItems、acceptableCategories、hardConstraints、softPreferences
   和 exclusions 必须在理解、规划、搜索、验证和发布链路中保持可追溯。
2. 硬约束数组不允许使用整组兜底为空的解析策略。单条无效约束必须单独进入结构化修复、
   追问或失败路径，不能清空其他有效约束。
3. 检索 query 必须保留自然语言。Provider 分类码只能用于解释返回事实，不能反向参与
   planning 或静默替代用户目标。
4. 目标语义关系必须与 action relation 一致。`exact` 只能表示与原目标相同；同义、扩大、
   替代需要分别记录，并按既有授权边界准入。
5. 最终发布边界必须独立核对硬约束、授权、目标新鲜度和必选目标证据。对 all-of 语义的
   必选目标，需要逐项覆盖，不能用非空匹配数组代替全部满足。
6. 证据必须有来源与获取时间。只有名称或分类时，系统应按规范区分支持与未知，不得把
   POI 分类直接提升为菜品供应证明。

### P2：业务效果与运行质量

1. 候选召回应先保留不同门店身份，在预算内渐进评估。预算允许限制检查数量，但未评估
   不等于不合格；上游选择阶段处理多样性，FinalGuard 和 UI 不重新选店或按品牌折叠。
2. 合格候选的排序应使用明确可解释的推荐效用，例如评分、价格、距离、偏好匹配和多样性；
   模型置信度只表示满足目标的把握，不等价于推荐质量。
3. 追问和补搜策略应基于真实失败原因，不以固定数量作为唯一停止目标。
4. 对明确目标、已有合格结果且不依赖扩词的路径，建议允许显式部分成功；开放探索仍可能
   依赖扩词。分批评估应保留成功批次，评估本身不是可省略的能力。此失败策略待评审，
   不允许静默降级或把未评估候选当成已验证。
5. 会话持久化应覆盖取消、失败和部分完成路径，便于恢复和诊断；是否引入更重的持久执行，
   需要先证明实际故障率和延迟需要该复杂度。
6. 观测指标应覆盖正常、追问、取消和失败轮次，并区分模型失败、Provider 失败、schema 失败、
   预算耗尽和 FinalGuard 拒绝。
7. 真实模型评测独立于 fixture eval，覆盖目标保真、硬约束、证据、延迟和成本；接受率、
   追问放弃率通过获准的产品观测统计，不能用模型模拟用户替代真实数据。

## 验收标准

- 对新菜品或复杂修饰词输入，搜索请求保留自然语言目标；内部改写可在 trace 中与原目标对照。
- 一个非法硬约束不会使其他硬约束消失；无效约束产生明确错误、修复或追问结果。
- `羊肉火锅` 不能在无授权情况下被规划成宽泛的 `火锅` 并继续使用 `exact` 授权语义。
- `无糖柠檬茶` 的“无糖”约束不会因为搜索改写而丢失。
- 只有名称或分类证据的目标，如果当前规范不允许提升为主推荐，则必须进入候补或返回未知，
  不能在 UI 中表述为已满足。
- all-of 必选目标缺少任一项证据时，该候选不能进入主推荐。
- FinalGuard 拒绝或降级候选时，trace 能对应显示原因；前端候补不会自动进入转盘。
- 模型或 Provider 失败不会把无证据候选伪装成通过；部分可用结果必须保留真实证据状态。
- fixture eval、真实模型 eval、trace 和业务指标分别报告各自能证明的内容，不互相替代。
- 主推荐数量下降时，UI 展示真实原因，不自动补位。

## 非目标

- 不要求把当前 workflow 重写为 Lead Agent、统一 Agent tool、model-tool loop 或 subagent
  lifecycle。
- 不承诺仅凭高德或 OSM POI 数据验证任意餐厅的实时完整菜单。
- 不要求一次性实现完整持久执行、跨请求幂等运行或复杂反馈学习系统。
- 不以固定搜索次数、固定推荐数量或固定模型调用次数作为质量目标。
- 不在本文授权通过关键词黑名单处理提示注入；安全防护应基于边界校验、结构化证据和输出
  语义校验。
